Subject: ESP32-S3 device IN endpoint buffer retirement and interrupt publication guarantees

We are reviewing ESP32-S3 USB-OTG device-mode HID IN on Arduino ESP32 3.3.0, SDK idf-release_v5.5-b66b5448-v1. This is a source/native-simulation investigation; we have NOT reproduced a silicon failure. The selected driver writes current xfer->buffer/total_len at dcd_dwc2.c:601–628 and reads the current transfer descriptor in IN handling:876–923. Its disable path:307–345 requests SNAK, waits INEPNE, requests EPDIS, waits EPDISD, acknowledges and flushes TX using epnum. TX FIFO allocation/control selection is at261–302. In a controlled native injection, submit old work, replace the current descriptor through direct raw DCD submission, then dispatch a completion; the handler reads current metadata. Normal stack busy protection is a different boundary. Adding an application token only to that reusable descriptor cannot authenticate old IRQ-origin work. This is a lifetime concern, not a claim the hardware generates impossible duplicate interrupts.

Questions that would change the decision:
1. What exact supported device IN NAK/disable/ack sequence establishes that old FIFO/buffer readers have stopped? Which status bits and applicable errata govern it? How should timeouts be handled without unsafe reuse?
2. Must flushing select the endpoint's allocated TX_FIFO_NUM rather than endpoint number? What is the mapping for nonidentity allocations, and which operations disturb EP0/CDC/MSC or other endpoints?
3. Which DIEPINT bits are W1C/read-only, what happens on simultaneous set/ack, and how must raw endpoint status, masks and already-pending CPU interrupts be ordered/drained?
4. At what documented point can no older controller/FIFO/IRQ work reference an old buffer or descriptor? Does transfer complete alone establish that, or is another fence required?
5. Which device/inter-core barriers and interrupt-affinity rules apply to this sequence? Does masking exclude an ISR already entered on the allocated core?
6. What supported method fences ISR publication already in progress and queued observers without deadlock or unbounded cross-core waits? Which guarantees belong to the application/stack rather than hardware?
7. Is there a supported public API or recommended stack/controller architecture providing bounded submission plus safe retirement, or a simpler documented ownership contract we should use?
8. Is the applicable material publicly available, available through support, or subject to separate terms? Please identify versions and applicability; this draft makes no agreement to those terms.

Answer checklist for review: applicable chip/mode/revision; complete ordered sequence; endpoint/FIFO scope; late-status exclusion; memory visibility; CPU/ISR/publisher fence; error/timeout retained ownership; supported API and exact limitations.
