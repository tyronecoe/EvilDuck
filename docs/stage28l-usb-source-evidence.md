**Raw `tud_hid_n_report` true is lower endpoint submission return after copying, not correlated completion.** It has no explicit completion wait/retry in the inspected entry function, but the compiled claim path can wait on a mutex. Raw false has multiple branches: invalid instance, claim refusal, post-claim length rejection or lower DCD failure. Current exact eight-byte valid input avoids length rejection, but a future interface must classify definite-not-submitted versus ambiguous side effects instead of blindly retrying every false.

**`USBHID::SendReport` true means readiness/submit and a semaphore take succeeded, not a proven per-action transfer.** Its comments explicitly mention extra/late semaphore gives. False can follow submission, so retrying it could duplicate output. Invoking it on the USB task risks waiting for work that same task must process; holding a lock needed by callbacks makes this worse. No future adapter should wrap it as a blocking Sink.

## Descriptor, framing and protocol

R backend uses `HID_REPORT_ID_KEYBOARD`; C `USBHID.h` defines that ID as 1, `USBHIDKeyboard.cpp:33–46` supplies `TUD_HID_REPORT_DESC_KEYBOARD(HID_REPORT_ID(...))`. S `hid_device.h:177–216` describes eight modifier bits, one reserved byte, six key bytes and a separate five-bit LED OUTPUT with padding. S `hid.h:357–363` is the packed eight-byte keyboard payload.

In the inspected SDK send path, nonzero ID produces **nine submitted bytes** (ID 1 + payload 8). ID 0 produces eight. The public callback header explicitly says composite buffer[0] is report ID; do not strip blindly or assume callback length is always eight. Failure may transfer a partial length. Proposed transport validation must bind negotiated protocol, instance, endpoint, report ID, payload length and full transfer length to an epoch; copying/comparing bytes is not identity.

C `USBHID.cpp:282–290` sets interface protocol only at the first constructor. R `hid_backend.cpp:12–22` constructs default-protocol HID before its FeedbackKeyboard in that translation unit; keyboard constructor uses KEYBOARD internally, default HID constructor uses NONE (`USBHID.h:75`). This source order does not certify absence of an earlier constructor elsewhere. The interface descriptor chooses fixed EP1 for keyboard protocol or allocator-chosen endpoints otherwise (`USBHID.cpp:194–215`); **no fixed endpoint/interface number or actual negotiated protocol is asserted here**. C wrapper `:348–362` normalizes ID to zero only when boot is supported/requested; R direct path bypasses that normalization. Existing ELF symbol review is not a full descriptor/constructor-order decode or bus capture.

CDC/MSC have separate classes but share controller/service scheduling. R legacy Keyboard.pressRaw/print/releaseAll (`hid_backend.cpp:110–119,251,356–389`) and core Keyboard.SendReport (`USBHIDKeyboard.cpp:77–80`) can reach the same HID IN path as raw scheduler updates. `USBHIDDevice` public methods (`USBHID.h:61–82`) expose descriptor/feature/output hooks, **no token-bearing completion registration**. App-level guards alone cannot exclude every producer/global core user. Source `USBHID::end` deletes semaphores/mutexes, not a documented endpoint/callback quiescence certificate.

No different release was substituted, no package upgraded, and no network retrieval used to guess that relation.

Consequently reset/disconnect/suspend/resume/protocol in-flight retirement, duplicate callback guarantees, event-queue flushing, DMA/buffer release and callback-source quiescence are **UNKNOWN**. The core source proves event flags/posting, not transfer retirement. Reconnect/ready/end/destructor/empty application queue cannot serve as a fence. Archive disassembly confirms selected call paths, not complete source or physical behavior. This blocker does not prevent a precise proposed contract; it prevents claiming the current stack implements it.
