# Stage28K actual synthetic contract implementation

Implementation lives only in `tests/stage28k/journal_driver.h/.cpp`; test policies/programs live in `test_journal.cpp`. No old API or operational firmware behavior changed. Scope: one driver-loop owner, persistent noncopyable Program + CompileSession + Bridge, memory Reader/context and opaque eight-byte snapshots. No production backend, File adapter, endpoint, RTOS task, USB callbacks, OS input or script-launched shell/network/file actions.

## Actual public-API feasibility and identity

The public counters in `language_preview/bridge.h:43–46` and implementations in `bridge.cpp:43–61,71–84` provide independent source admissions, keyboard acknowledgements, Delay acknowledgements and acknowledgement tick. Planner exposes pending snapshot, phase and state (`keyboard.h:42–48`); Bridge exposes intent/state. One serialized step performs either a Planner attempt or Runtime tick. Successful keyboard source admission increments `admissions()` on a Runtime tick **before any report callback**. The wrapper creates E from that delta after the tick; the following report phase receives E. It does not read private fields, guess an E from bytes or reinterpret queueing as source ack.

Tap press and restoration get different R values but retain the admitted E. A source HOLD/RELEASE is one Held phase; equal snapshots of subsequent source admissions get distinct E/R. Exact source opcode/value is not exposed to this wrapper and is not claimed by the journal: its action kind is Planner phase, its source kind Keyboard or Delay. Keyboard E is acknowledged only when `keyboardAcks()` changes after all its report phases. Delay has no report action; `delayAcks()` provides its acceptance tick and the wrapper commits one Delay E/ack. No fabricated transport completion exists.

**Conservative observability boundary:** there is no public next-source-event hook. Before a Runtime tick with no current intent, the wrapper checks that an E ID and intent slot could be allocated. That guards Delay acceptance within the tick, without changing Bridge. It does not allocate E for a tick with no event. At E counter/intent capacity exhaustion it may stop before a non-event tick, including waiting/completion of the last Delay, rather than distinguish an unobservable next event. This fail-closed harness policy is explicit and tested, not a widened source cap or a claim of exact last-ID progress. Future owners must review this conservative barrier before selecting a less restrictive design; no source hook is added here.

S/E/R use checked monotonic uint64 counters, never wrap or reuse **within one Driver identity lifetime**. Fixture Drivers have independent disconnected contexts/journals. Destruction never sends a report; reconstruction while retaining callbacks is prohibited by the lifetime contract. No global uniqueness across reconstructed objects or callback safety after a dangling context is claimed. Begin consumes a unique S even if Bridge later rejects; E/R exhaustion fails before assigning a new ID. Counter seeds are constructor-only synthetic boundary inputs, not a mutable runtime reset interface.

## Fixed admission/acceptance journal

Capacities selected before tests: **256 action records, 128 source-intent records, eight setup requests**. They cover finite T01–T18 fixtures and leave bounded fault cases. Long valid preview loops can exhaust this independent evidence capacity; they fail closed rather than overwrite history or enlarge old execution limits.

Each action record retains S/E/R, immutable intended snapshot, independent accepted-snapshot field, phase, attempts, outcome, receipt state and acceptance tick. One outstanding record is Pending; repeated Retry retains identity and bytes. Retry creates no accepted receipt. On Accepted the callback copies exactly eight bytes into `acceptedSnapshot` once and marks that current record Accepted. Press acceptance allows restoration; final acceptance only makes E Ackable in Bridge, not acknowledged yet. Rejected/abandoned pending records stay in history; their zero-initialized accepted field is **not** evidence of accepted neutral. Initial sync/setup/drain use E=0. Overflow denies an attempt before any new action is offered. No vectors, growth, ring overwrites or reclamation.

The source-intent journal records ordinal S/E, Keyboard/Delay kind, admitted/ack ticks, accepted report count and exactly-once ack state. Runner cross-checks action-to-intent relationships and cancelled-intent zero-ack behavior. A successful mock receipt is not USB queue admission, completion, OS input or host key release. `completionNotice` is bounded diagnostic input only and always rejects use as acceptance, even for matching IDs; correlated completion mode remains unselected.

## Scheduling, ownership, cancellation and faults

`step(now)` processes at most one ordinary setup request then at most one Planner report attempt **or** Runtime tick. Request processing can schedule an action, not execute a second tick. No spinning on Retry, sleeping or blocking wait. Work counters explicitly account for the Runtime deadline path even when a report is pending. Caller clocks use unchanged unsigned elapsed comparisons and limits: Planner 256 attempts / 30,000 ms; Runtime 10,000 steps / 100,000 ticks / 30,000 ms; CompileSession 65,536 steps. T14 tests elapsed 31 versus exact 32 across a small uint32 wrap. Backward clocks/full-cycle sampling gaps are outside contract; no production dwell, default delay or jitter added.

Setup claims are limited to owners 0–2 while Prepared. Script owner 3 is controlled by unchanged Bridge during execution. No competing live producer exists. Planner's atomic six-key/held-tap guards are observed, not reimplemented. Source modifier commands remain blocked; Prepared SHIFT uses the existing mock API only. All mutating begin/start/hold/release/drain/nested-step calls during callbacks reject/no-op; the callback can only request deferred cancellation, deferred mock loss or bounded setup handoff. No cross-thread safety is promised.

Cancel/STOP uses a priority bit independent of ordinary queue saturation. Callback-originated cancellation is applied after the callback returns: valid already-offered acceptance is journaled, but E cannot later ack or resume. Deferred mock loss becomes a first fault after the callback and leaves uncertainty. Normal completion, STOP, error or cancel clears logical owners and pending work but is **TerminalUndrained**, even if the old accepted snapshot is zero. Explicit drain gets a fresh zero R; only its current Accepted record permits Drained and a new session, whose sync also needs a fresh receipt. No neutral receipt is sent by destructor or cancellation itself. Drain refusal/timeout/full journal denies restart.

Diagnostics are fixed: first fault and associated Bridge diagnostic are retained; subsequent fault does not overwrite them. Last rejection/count and observation count are bounded/saturating, not logs with unbounded growth. Queue overflow returns false visibly; setup errors expose a rejection without partially adding ownership. Sink exceptions, including simulated `bad_alloc`, become Failed rather than fabricated success. First faults remain historical across drains/new sessions; no repair or erase route exists.

Reader callbacks/context/source must remain valid and bytes stable through compilation. Wrapper keeps its own MemoryReader, not the source bytes; tests use literals or bounded synthetic arrays. Compile terminal detaches callbacks. Program remains alive through Runtime observation, diagnostics and drain; Bridge contains Runtime/Planner; CompileSession contains its Compiler. Destructor cancels compile/runtime without callback output. Caller lifetime mistakes remain caller violations; sanitizer tests prove only the exercised valid/negative mock paths, not arbitrary external dangling-pointer immunity.

All 18 Stage28J traces have actual new executions. No trace was weakened into tabletop-only status or blocked implementation marked PASS. No production semantic hook was necessary. The conservative E reservation, diagnostic-only notices, journal capacity and object lifetime scope are explicit limits to review, not authorization for future integration.
